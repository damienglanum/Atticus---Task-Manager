01 / Overview

Your side project already has enough infrastructure.

Atticus is one desktop application holding every personal codebase you keep returning to. It runs from a single SQLite file, it answers to nobody, and it is built for the size of problem one developer actually has.

  1. 01 / Private

    Project data stays here

    Tasks, notes, and file references live in a SQLite database on your disk, at a path the application shows you. Nothing about your work is uploaded, synced, or tracked.

  2. 02 / Focused

    One developer, no theatre

    No assignees, no comments, no activity feed, no standups. Everything on screen is something you can act on, because there is nobody else to wait for.

  3. 03 / Recoverable

    Backup, export, restore, undo

    Snapshots are taken before migrations and destructive operations, JSON export and import are versioned, and a restore backs up the current database first.

  4. 04 / Open

    MIT, and inspectable

    The application, its schema, its decision records, and the workflow that signs the builds are all in the repository. Read them before you trust them.

02 / Principles

Three principles, and the screens that carry them.

Every image below is the application as it actually renders, captured by the end-to-end suite. Nothing here is a mockup.

01

Return without rereading the repo.

Three weeks away from a project and the question is never “what does this code do” — it is “what was I in the middle of”. Projects, boards, columns, and a work-in-progress limit answer that before you open the editor.

When the memory is a fragment rather than a place, ⌘K searches every project at once and tells you which board and column the match sits in.

  • StructureProjects → boards → ordered columns
  • LimitsOptional WIP ceiling per column, flagged when breached
  • RecallGlobal search, board filters, saved filters

02

Context belongs beside the task.

A decision written into a commit message is a decision you will never find again. Project notes are Markdown documents that live with the project and can be linked to the tasks they explain — the note names its tasks, and each task names its note.

The task editor carries the rest: a Markdown description, a checklist, priority, due date, estimate, tags, links, and references to real files on your disk. References store the path, never a copy, and say so plainly when the file has moved.

  • NotesPer project, full-text searchable, linked to tasks
  • TaskMarkdown, subtasks, labels, estimate, due date
  • FilesLocal paths by reference, with a visible missing state

03

Move work your way.

A card can be dragged with the pointer, picked up and moved with the keyboard, or sent somewhere from an explicit “Move to…” command. All three write the same transaction, and every move is announced and undoable with ⌘Z.

This matters more than it sounds. Drag is a lovely gesture and a terrible sole route: it fails a trackpad you are fighting, a keyboard-only session, and anyone who cannot perform it at all.

  • PointerDrag and drop, with a lifted overlay
  • KeyboardPick up, move, drop — focus returns to the card
  • MenuExplicit “Move to…” from the card actions

03 / Local MCP boundary

Local AI, hard boundary.

Atticus ships a permissioned MCP server inside the same executable. Codex, Claude, and other stdio clients can read your workspace when you allow it — and can only write inside a sandbox they created themselves. Access is off until you turn it on.

Zone A · user-owned

Your projects

Read
Permitted once you enable access
Write
Refused, in every mode

Every project you made yourself. Note bodies and task detail are readable so a model can plan from them; nothing it sends can change them, including when it knows the identifiers. Archived work is read-only too.

Enforced in the database

Zone B · MCP-created

AI Boards

Read
Permitted once you enable access
Write
Permitted, inside this zone only

Projects the server created carry a persistent marker and appear under a collapsible AI Boards section in the sidebar. Inside it a client may create and maintain work. Delete, archive, restore, and removal tools are not exposed at all.

  • DefaultOff. The tool catalogue is visible; calls are refused.
  • PolicyRe-read before every call, so a change lands without reconnecting
  • Transportstdio, launched by your client. No HTTP port is opened.
  • FilesSeparate opt-in; a path must sit under the project’s folder, and contents are never read
  • ContractVersioned workflow instructions, strict schemas, and structured errors on every connection

Setup, tool contracts, and the recovery recipes are documented in docs/mcp.md.

After installing. The AppImage needs the executable bit before it will run. On macOS the first launch of any unsigned build goes through Open Anyway in System Settings → Privacy & Security. Updates afterwards are checked at launch and every thirty minutes, and verified against a public key committed in the repository.
